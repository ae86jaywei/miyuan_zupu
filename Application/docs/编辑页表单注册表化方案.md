# 编辑页表单注册表化方案

> 目标：`PersonEdit.ets` 从 2,836 行继续下降，字段表单由 `Person.FIELD_METAS` 驱动。
> 状态：方案文档，**未改动编辑页核心逻辑**。建议在真机回归通过后执行。

---

## 一、现状

| 项 | 数值 |
|---|---|
| `PersonEdit.ets` | 2,836 行 |
| `Person.FIELD_METAS` | 38 个字段 |
| 表单控件 | `SelectField / PersonPickerField / DateFieldInput` 已抽到 `components/form` |
| 字段渲染 | 每个字段一段手写 `TextField / SelectField / 日期 / 人员选择` |
| 保存 | `fill()` 逐字段读、`toPerson()` 逐字段写、`formSnapshot()` 逐字段拼 |

**问题**：
- 新增字段要同时改 `FIELD_METAS`、`PersonEdit` 的 UI、`fill`、`toPerson`、`formSnapshot`、详情页。
- `FIELD_METAS` 已经包含 `key/label/hint/group/type/privacy`，但 UI 只用到了 label/hint。
- 上次新增 `marriageStatus / spouseFamily / fatherLifeStatus` 时，编辑页需要手工加 3 段 UI + 3 处读写。

---

## 二、目标结构

```text
model/FieldRegistry.ets（已有）
  └─ FIELD_METAS
       ↓
model/FieldEditorSpec.ets（新增）
  └─ 把 type 映射为编辑器类型与选项
       ↓
components/form/PersonFieldForm.ets（新增）
  └─ 按 group 分组渲染，内部选择 TextField / SelectField / DateFieldInput / PersonPickerField
       ↓
pages/PersonEdit.ets
  └─ 只保留：加载、校验、特殊区块（配偶、媒体、墓葬定位）、保存
```

### 2.1 编辑器类型映射

| `FIELD_METAS.type` | 控件 | 说明 |
|---|---|---|
| `text` | `TextField` | 普通文本 |
| `number` | `TextField`（数字键盘） | 世代 |
| `select` | `SelectField` | 选项来自 `Enums` / `Person` 常量 |
| `relation` | `PersonPickerField` | 父亲/母亲等 UID 选择 |
| `grave` | 文本 + GPS 按钮 | 墓葬信息 |
| `image` | 头像上传 | 保留自定义 |
| `media` | 相册/视频 | 保留自定义 |

### 2.2 选项来源

`FIELD_METAS` 目前没有 `options`。在 `FieldEditorSpec` 中按 key 映射：

```ts
export function editorOptions(key: string): string[] {
  if (key === 'gender') return GENDER_OPTIONS;
  if (key === 'lifeStatus') return LIFE_STATUS_OPTIONS;
  if (key === 'childStatus') return CHILD_STATUS_OPTIONS;
  if (key === 'childMark') return CHILD_MARK_OPTIONS;
  if (key === 'rank') return RANK_OPTIONS;
  if (key === 'marriageStatus') return MARRIAGE_OPTIONS;
  return [];
}
```

后续可把 `options` 直接加进 `FieldMeta`，彻底去掉这段映射。

## 三、渲染流程

```text
for group of FIELD_GROUPS:
  GroupHeader(group)
  for meta of FIELD_METAS where meta.group === group:
    if meta.key 在自定义区块（spouses/photos/videos/avatar/grave 定位）:
      continue
    PersonFieldForm({
      meta,
      value: this.valueOf(meta.key),
      onChange: (v) => this.assignValue(meta.key, v)
    })
```

`valueOf` / `assignValue` 仍是 switch，但只保留**读写**，UI 不再逐字段手写。

---

## 四、保留的自定义区块

这些字段不适合通用表单，继续手写：

| 字段 | 原因 |
|---|---|
| `spouses` | 多配偶、名分、排序，已有 `SpouseSection` |
| `avatar` | 头像裁剪/上传 |
| `photos` / `videos` | 多选媒体与预览 |
| `graveLng` / `graveLat` / `graveAltitude` | GPS 拾取、地图选点 |
| `uid` | 自动生成，通常只读 |
| `createdAt` / `updatedAt` | 系统字段，不展示 |

## 五、迁移步骤

### 5A：只读渲染（不改保存）

1. 新增 `FieldEditorSpec`，把类型/选项/占位文案映射好。
2. 新增 `PersonFieldForm`，先只在“身份标识”分组替换 6~8 个纯文本字段。
3. `fill` 不变，`onChange` 仍调用现有 `this.fXxx = v`。
4. 构建 + 回归：确认输入、清空、简繁切换、深色模式正常。

### 5B：扩展到全部文本/选择字段

1. 逐个分组替换，保留 `身份`、`标记`、`婚配状态` 等有联动逻辑的字段。
2. 联动逻辑（如 `isNatalOutsider` 影响排行提示）通过 `hint` 动态传入。

### 5C：收敛读写

1. `fill` / `toPerson` 改为 `valueOf` / `assignValue` 的 switch。
2. `formSnapshot` 改为遍历 `FIELD_METAS` 的 key + 值数组（仍需 switch 读值）。

## 六、风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| ArkUI `@Builder` 按值传参不刷新 | 之前 `SelectField` 已踩过 | 继续用“子组件 + @Prop” |
| `@Prop` 数组/对象深拷贝 | `options` 每次渲染新数组可能触发重建 | 在页面级缓存 options |
| 联动字段被误通用化 | 婚配状态/排行/身份有互相影响 | 保留手写或传动态 hint |
| 动态 key 访问 | ArkTS 不支持 `p[key]` | `valueOf/assignValue` 保留 switch |
| 性能 | 38 个字段全量重绘 | 分组 + 条件渲染，避免 `build` 内查 DB |

---

## 七、验证清单

1. 每个字段：输入 → 保存 → 返回 → 重新进入，值不丢。
2. 清空字段后保存，数据库为空而不是旧值。
3. 未保存返回提示仍能识别所有字段变更（`formSnapshot` 覆盖）。
4. 简繁切换、深色模式、窄屏双列布局正常。
5. 新增字段只改 `FIELD_METAS` 就能出现在表单（目标验收）。

---

## 八、结论

编辑页注册表化可以把 38 个字段的 UI 手写量降到“一个通用组件 + 一张映射表”，但要分三次迁移，且必须在 DevEco 真机回归中逐步验证。当前 P0 刚通过，不建议立刻大改；等回归稳定后再按 5A → 5B → 5C 推进。
