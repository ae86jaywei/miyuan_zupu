# 鸿蒙版族谱应用：海量节点展示与交互优化方案

## 一、问题描述

在开发鸿蒙版族谱应用时，面对数千至数十万规模的家族节点，当前采用了"欧式谱（横轴世系图）"和"苏式谱（竖式吊线图）"将所有族人展示在同一棵家族树上。在此场景下，暴露出以下三大核心问题：

### 1. 缩放与细节的矛盾（视口迷失）
- 放大画布时，能看清人员卡片内容，但视野范围变小，很难移动去寻找其他族人。
- 缩小画布时，能看到更多人，但文字糊成一团，无法看清卡片内容。

### 2. 缩放锚点错误（焦点丢失）
- 改造前通过拖动滑块控制缩放比例，缩放时内容会向画布左上角（默认原点）聚拢或散开，原本在屏幕中间的人物会跑出屏幕，用户必须重新拖拽寻找。
- 改造前缺失"以双指中心为固定点"的平移＋缩放手势交互。

### 3. 分页方案失败（连续性割裂）
- 曾尝试使用分页处理，但由于家族树是强关联的网状／树状结构，分页切断了世代间的上下衔接。
- 导致页面看起来支离破碎，某些页面甚至只有1-3个人，极度浪费空间，不符合族谱的阅读习惯。

## 二、问题根因

### 1. 交互逻辑缺陷
滑块缩放采用的是基于原点的数学变换，而非基于视口（相机）矩阵的锚点变换。没有引入手势事件（PinchGesture）来动态获取缩放中心点。

### 2. 渲染模型不合理
采用了"全量渲染"策略。无论屏幕内还是屏幕外，所有几千／几万个节点都在参与绘制和布局计算。当放大时，系统依然承载着庞大的数据处理开销，导致手势响应迟滞。

### 3. 缺乏多尺度表达（LOD）
试图用一种视觉形态（完整卡片＋连线）应对所有缩放级别。没有根据缩放比例动态改变信息的呈现精度。

### 4. 违背了无限画布的本质
分页方案试图用"物理切断"来减少单次渲染量，但这破坏了血缘树天然的"无限延伸"的连续感。

## 三、解决方法

针对以上问题，需要从交互重构、渲染架构、视觉层次三个维度进行系统性改造。

### 3.1 交互体验重构：固定锚点的手势缩放与平移

放弃滑块控制缩放，引入鸿蒙 PinchGesture（双指捏合）与 PanGesture（单指拖拽）。

**核心数学原理**：当双指捏合时，以双指中心点为锚点，计算新的平移量 (offsetX, offsetY)，确保锚点处的内容在缩放前后的屏幕位置不变。

**变换约定**（必须与组件层级一致）：

```
屏幕坐标 = 内容坐标 × zoom + offset
```

落地上采用「外层容器 `translate(offset)`、内层内容 `scale(zoom, center=0,0)`」两层结构，避免把 `scale` 和 `translate` 加在同一节点上导致平移量被二次缩放。

**正确计算公式**：

- `ratio = newScale / startScale`（相对**手势起点**，不是相对上一帧）
- `newOffsetX = currentCenterX - (startCenterX - startOffsetX) * ratio`
- `newOffsetY = currentCenterY - (startCenterY - startOffsetY) * ratio`

其中 `startCenter` 是手势按下时的双指中心，`currentCenter` 是当前帧的双指中心；两者不同，才能在捏合的同时跟随双指整体平移。

> ⚠️ 原文 `ratio = newScale / this.scaleValue` 是错误的：`this.scaleValue` 在上一帧 `onActionUpdate` 中已被覆盖，第二帧起 `ratio` 会变成相邻帧的增量比，而 `lastOffset` 仍是手势起点的偏移，两者不同源，锚点会漂移。
>
> ⚠️ 原文 `centerX - (centerX - lastOffsetX) * ratio` 复用了同一个 `centerX`，只适用于「双指中心静止不动」的理想情况；实际捏合时中心会移动。

**鸿蒙 ArkTS 落地代码**（与当前 `view/TreeCanvas.ets` 实现一致）：

```typescript
// 缩放上下限：0.05 ~ 1.5（下限留给超大族谱全览）
.onActionStart((event: GestureEvent): void => {
  this.startScale = this.scaleValue;
  this.startOffsetX = this.offsetX;
  this.startOffsetY = this.offsetY;
  // 部分设备可能给出 0，回退到视口中心，避免锚点飞到左上角
  this.startCenterX = event.pinchCenterX > 0 ? event.pinchCenterX : this.viewW / 2;
  this.startCenterY = event.pinchCenterY > 0 ? event.pinchCenterY : this.viewH / 2;
})
.onActionUpdate((event: GestureEvent): void => {
  const next: number = this.clampZoom(this.startScale * event.scale); // event.scale 是相对起点的累计比例
  const ratio: number = next / this.startScale;
  const cx: number = event.pinchCenterX > 0 ? event.pinchCenterX : this.startCenterX;
  const cy: number = event.pinchCenterY > 0 ? event.pinchCenterY : this.startCenterY;
  this.offsetX = cx - (this.startCenterX - this.startOffsetX) * ratio;
  this.offsetY = cy - (this.startCenterY - this.startOffsetY) * ratio;
  this.scaleValue = next;
})
```

**必须补充的两点**：

1. 每次写入 offset 后要按内容尺寸与视口尺寸做边界钳制（当前用 `ViewportMath.clampScreenOffset`），否则内容会被拖出屏幕且无法找回。
2. `PanGesture` 要限定 `fingers: 1` 并设置最小距离（当前为 `distance: 8`），与 `PinchGesture({ fingers: 2 })` 放进 `GestureGroup(GestureMode.Parallel)`，避免单指平移与双指缩放互相抢占。

**关于滑块**：本项目已彻底移除缩放 Slider（全工程无 `Slider`、无 `gpZoom`），也不需要再讨论「保留滑块时锚点设为屏幕中心」的兼容方案。

### 3.2 渲染架构优化：视口驱动与按需渲染（Viewport Culling）

解决海量节点卡顿的根本方案，是只渲染当前屏幕（视口）及预加载缓冲区内的人。

1. **视口裁剪**：由 `offsetX/offsetY/zoom/viewWidth/viewHeight` 反算内容坐标下的可视矩形，并把半屏缓冲并入：
   - `contentX = -offsetX / zoom - margin`
   - `contentY = -offsetY / zoom - margin`
   - `contentW = viewWidth / zoom + margin * 2`
   - `contentH = viewHeight / zoom + margin * 2`

   当前由 `service/TreeViewport.ets`（`ViewportMath.contentRect`）与 `TreeCuller.euBoxes/lines` 实现，只有与矩形相交的卡片和连线才进入 `ForEach`。视口 key 由 `TreeCanvasShared.treeViewKey` 组装，参数不变时直接跳过裁剪。

2. **布局缓存，而不是“务必 Worker”**：族谱树坐标计算确实耗时，但 ArkUI 的组件树必须在主线程构建，Worker 只能承担纯计算，回传数千节点的几何数据还要做结构化克隆/序列化，通信成本可能抵消收益。本项目采用更稳妥的做法：
   - `TreeLayoutCache` 按宗支缓存 `EuCanvas/SuCanvas`，布局只在数据版本、卡片宽度、谱式变化时失效；
   - `TreeCanvas` 只对当前谱式与需要显示的宗支取布局，不一次性构建全部；
   - 若未来单宗支规模超过实测阈值（例如裁剪本身 > 16ms），再把**纯布局函数**抽成无 UI 依赖的模块放进 Worker，先做基准测试再决定，不要把 Worker 当作默认答案。

3. **分层渲染机制**（当前实现与可选项）：
   - 现状态：连线与卡片同处一个 `Stack`，连线用轻量 `Row` 组件绘制（只为可见线创建），卡片用 `TreeMiniCard`/骨架块。外层容器 `translate(offset)`，内层内容 `scale(zoom)`，手势期间只改这两个变换。
   - 可选优化：把连线改为 `Canvas` 单次绘制。理论上能减少大量 `Row` 节点，但会引入 Canvas 与卡片层的坐标同步、重绘时机和高分屏适配问题；当前可见连线数量已受视口裁剪限制，**不建议在 1.04 版本做这项重构**。
   - 手势期间不要重建卡片内容，只更新缩放矩阵与裁剪窗口；抬手后再做一次完整精度恢复（项目用 `interacting` 标志实现）。

### 3.3 视觉层次优化：多尺度细节层次（LOD - Level of Detail）

不要在任何缩放级别都绘制卡片。借鉴地图 App，根据缩放比例切换视觉形态。当前实现（`TreeCanvasShared.detailLevelOf`）的阈值与形态：

- **极低缩放（zoom < 0.36，全局概览）**：聚合气泡。按固定 **72vp 屏幕网格**把节点聚合，气泡半径按 `min(sqrt(人数), 5)` 增长，颜色按女性占比区分，气泡中心标注人数；点击气泡放大到 0.85。
- **中等缩放（0.36 ≤ zoom < 0.68，局部浏览）**：骨架模式。保留连线骨架，节点只显示姓名前两个字（`shortName`），边框/字号按 `1/zoom` 反算，保证屏幕观感稳定。
- **高缩放（zoom ≥ 0.68，精细查看）**：完整卡片。显示姓名、字号、配偶、子女数等信息。
- **手势进行中**：在以上档位基础上再降一级（聚合档除外），抬手后恢复，避免 `PinchGesture` 每帧重建大量卡片。

> 原文“气泡颜色代表人口数量”与实际不符：当前颜色编码的是性别比例，人口数量由气泡半径和中心数字表达。阈值也应写死为代码中的 `0.36` / `0.68`，避免实现与文档各说一套。

### 3.4 性能兜底体验优化

1. **手势防抖与节流**：`PinchGesture.onActionUpdate` 触发极快。当前实现：
   - `onActionStart` 记下起点缩放/偏移/双指中心，`onActionUpdate` 只做矩阵计算和边界钳制；
   - 手势期间 `interacting = true`，LOD 主动降一级，避免每帧重建完整卡片；
   - `onActionEnd` 恢复 `interacting = false` 并补一次高精度裁剪。
   - **仍存在的代价点**：当前每帧 `update` 都会重算画布尺寸并按新视口 key 重新裁剪，超大树下可能接近 16ms。若真机压测掉帧，应改为「手势中只改 `translate/scale`，抬手后再裁剪」，而不是继续加节流定时器。

2. **提供“一键复位”**：`TreeCanvas.ViewTools` 已提供悬浮「全览」按钮，调用 `resetView()`：
   - 取各宗支内容宽高的最大值，按 `min(viewW / contentW, viewH / contentH, 1)` 求适配比例；
   - 将 `scaleValue` 设为该比例，重新计算画布尺寸并把内容居中；
   - 缩放值始终钳制在 `[0.05, 1.5]`，偏移用 `ViewportMath.clampScreenOffset` 保证四角可达。

3. **可观测性**：`TreePerf` 已记录裁剪与分组耗时，真机验证时应以 HiLog 中的 `cull_eu` / `cull_su` / `tree_groups` 指标判断是否需要进一步优化，而不是凭感觉加 Worker 或 Canvas。
