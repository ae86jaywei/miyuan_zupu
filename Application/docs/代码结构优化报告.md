## 三、重复与可复用清单

### 3.1 表单控件（优先级：高）

| 现状 | 位置 | 问题 |
|---|---|---|
| `SelectField` | `pages/PersonEdit.ets:39` | 私有组件，其他页面不能用 |
| `PersonPickerField` | `pages/PersonEdit.ets:162` | 私有，人物搜索选择逻辑无法复用 |
| `DateFieldInput` | `pages/PersonEdit.ets:370` | 私有，日期选择与 CalendarPage 分离 |
| 搜索框 | `PersonEdit:229`、`FamilyDirectoryView:314`、`GraveMap:405`、`TreeCanvas:1276` | 4 处重复的 `TextInput` 样式与清空逻辑 |
| 直接 `TextInput` | 11 个页面/视图 | 输入框高度、圆角、底色各写一遍 |

**建议公共模块：**

```
components/form/
  SelectField.ets        // 现有 PersonEdit 版迁出
  TextField.ets          // 统一 label/hint/required/清除
  PersonPickerField.ets
  DateFieldInput.ets
  SearchField.ets
  FormSection.ets
```

统一事件契约：`onValue: (v: string) => void`、`onPick: (p: Person) => void`，避免每个页面自定义回调。

### 3.2 字段元数据（优先级：最高）

同一个 `Person` 字段目前在这些地方重复维护：

| # | 位置 | 维护内容 |
|---|---|---|
| 1 | `model/Person.ets:393` `FIELD` | key / label / hint / group / type / privacy |
| 2 | `pages/PersonEdit.ets` | 每个字段一份 `TextField/SelectField` + fill + toPerson |
| 3 | `view/PersonDetailPanel.ets:145-230` | 每个字段手写 `InfoRow` 与格式化 |
| 4 | `service/GenealogyService.ets` | 建表列、`ensureColumn`、values、select |
| 5 | `model/CloudModels.ets:245-280` | 云端 payload 逐字段映射 |
| 6 | `service/FamilySyncService.ets:408-450` | sync-pull 逐字段映射 |
| 7 | `service/PatchUtil.ets:84-215` | 字段白名单、textOf、numberOf、boolOf、中文名 |
| 8 | `service/ExportService.ets:44-120 / 390-490` | CSV 列名、导出、导入 |
| 9 | `service/ImportPlanner.ets:690-710` | 合并策略 |
| 10 | `CloudProgram/cloudfunctions/_shared/patch.js:11-15 / 135-142` | 云函数白名单与中文名 |

**后果：** 每次新增字段（如本次 `fatherLifeStatus`、`marriageStatus`）要改 10 个文件，漏一处就出现“保存不生效”或“云同步丢失”。

**建议：字段注册表单一来源**

```ts
// model/FieldRegistry.ets
export interface FieldDef {
  key: string;
  label: string;        // 唯一中文名
  hint: string;
  group: string;
  type: 'text' | 'number' | 'boolean' | 'select' | 'date' | 'relation';
  privacy: boolean;
  cloud: boolean;       // 是否上云
  csv: boolean;         // 是否进 CSV
  db: string;           // SQLite 列名
  options?: string[];
}
export const PERSON_FIELDS: FieldDef[] = [ ... ];
```

由它派生：
- `ensureColumn` / SQL values 映射
- 云端 payload 序列化
- 协作补丁白名单与中文名
- CSV 表头与导入
- 编辑页表单（通用 `PersonFieldForm`）
- 详情页只读区（通用 `PersonFieldView`）

云函数仍单独保留一份白名单（安全边界），但可由构建脚本从 FieldRegistry 生成，避免手改。

### 3.3 选项常量（优先级：中）

已集中的（好）：

| 常量 | 位置 | 使用 |
|---|---|---|
| `GENDER_OPTIONS` | `model/Enums.ets:11` | 性别 |
| `LIFE_STATUS_OPTIONS` | `model/Enums.ets:21` | 在世状态 |
| `CALENDAR_OPTIONS` | `model/Enums.ets:44` | 公历/农历 |
| `RANK_OPTIONS` | `model/Enums.ets:102` | 排行 |
| `CHILD_MARK_OPTIONS` | `model/Enums.ets:107` | 标记 |
| `SPOUSE_RELATIONS` | `model/Person.ets:99` | 配偶名分 |
| `CHILD_STATUS_OPTIONS` | `model/Person.ets:178` | 身份 |

仍有问题：

1. **硬编码选项**：`PersonEdit.ets:2759 / 2775` 的 `['在世', '已故']`（父名/母名状态）应改为 `LIFE_STATUS_OPTIONS` 的子集常量。
2. **场景不适用的选项**：`RANK_OPTIONS` 含“随母子/随母女”，娘家排行已过滤，但本族排行下拉仍会出现；建议拆成 `CHILD_RANK_OPTIONS` 与 `NATAL_RANK_OPTIONS`。
3. **语义重叠**：`CHILD_STATUS_OPTIONS` 同时包含“嫡出/庶出…”和“元配/继室/侧室/偏房…”，与 `SPOUSE_RELATIONS`（配偶名分）重复。同一个人可能两处填不同值。
   - 建议：拆分 `childOriginOptions`（出身）与 `personRankOptions`（本人名分），或明确“身份”只存出身，妻妾名分只存配偶关系。
4. **无场景元数据**：选项只有字符串，没有 `hint/gender/scene`，导致各页面各自判断（如婚配状态按性别切换）。
   - 建议：`OptionItem { value, label, hint, gender?: '男'|'女', scene?: string }`。

## 五、目标结构（HarmonyOS 官方推荐）

官方推荐的核心点：**分层、模块化（HAR/HSP）、组件化、资源化、统一状态管理、长列表复用**。

### 5.1 模块划分

```
Application/
├── common/                     # HAR：与业务无关
│   ├── base/                   # 模型基类、枚举、常量、工具
│   │   ├── model/              # Person/Genealogy 等纯数据
│   │   ├── enums/              # OptionItem、状态枚举
│   │   ├── util/               # 文本、日期、ID、补丁
│   │   └── theme/              # 颜色/尺寸/字体 token
│   └── ui/                     # HAR：通用 UI
│       ├── components/         # TS/PageHeader/EmptyHint/StatCard...
│       ├── form/               # SelectField/TextField/DateField/SearchBar
│       └── layout/             # Section/DetailSection/FormSection
├── entry/                      # 壳工程：路由、启动、装配
│   └── src/main/ets/
│       ├── pages/              # 只做路由与装配
│       └── features/
│           ├── person/         # PersonEdit/PersonDetail/PersonCard
│           ├── tree/           # TreeCanvas + 7 种风格 + shared
│           ├── export/         # 牒记 PDF/卡片 PDF/CSV/导入
│           ├── family/         # 首页/成员/目录/云同步入口
│           └── settings/       # 设置/主题/简繁
├── service/                    # 可选 HAR：领域服务
│   ├── repository/             # PersonRepository/BookRepository
│   ├── cloud/                  # CloudFacade + Backup/Pull/Publish/Outbox
│   ├── pdf/                    # PdfMeasure/PdfTheme/PdfMemoryGuard
│   └── text/                   # DieJiText（只保留牒记文案）
└── resources/
    └── base/element/
        ├── color.json          # 品牌色/语义色
        ├── string.json         # 固定文案
        └── float.json          # 间距/字号/圆角
```

### 5.2 关键规范

1. **状态管理**
   - 全局：`AppStorage` 只放 `darkMode`、`gpScript`、`windowWidth`、`currentBookKey`。
   - 页面：`@State`；跨组件：`@Link/@Prop`；跨页面：`@Provide/@Consume` 或 Store。
   - 禁止在 `build()` 中查数据库（当前 `PersonEdit.isNatalOutsider()` 每次重绘都会 `getPerson`，应缓存为 `@State`）。

2. **组件规范**
   - 通用组件不依赖 service；业务组件通过参数/回调注入数据。
   - 长列表使用 `LazyForEach` + `@Reusable`（人物列表、树卡片）。
   - 统一 `@Builder` 复用小组件（当前各页面大量重复 `Row+Text`）。

3. **资源规范**
   - 颜色/字号/间距进 `resources`，组件用 `$r()`。
   - 固定中文文案进 `string.json`；简繁转换仍由 `T()` 统一处理。

4. **性能规范**
   - 树视口：保持现有 `TreeCanvasShared` 的裁剪与 `detailLevelOf`。
   - PDF：合并内存看门狗，统一软/硬阈值配置。
   - 避免在页面 `build()` 中做排序/查询/字符串拼接（当前多处）。

## 六、实施路线

4. 硬编码颜色归 Theme（PersonEdit/ImportExport/Index/GraveMap/FamilyHome）。
5. 统一顶栏：新增 `PageHeader`，替换 5 处手写。

### 阶段 2：字段注册表
1. 建 `model/FieldRegistry.ets`，把 `Person.FIELD` 扩展为完整元数据（db/cloud/csv/type/options）。
2. 由注册表生成：
   - `GenealogyService` 的列与 values/select
   - `CloudModels` / `FamilySyncService` 映射
   - `PatchUtil` 白名单与中文名
   - `ExportService` 表头与导入
   - 编辑页通用表单、详情页通用只读区
3. 云函数白名单由脚本从注册表生成（保留独立文件，避免运行时依赖）。

### 阶段 3：PDF 与服务收敛
1. 抽 `service/pdf/PdfMeasure/PdfTheme/PdfMemoryGuard/PdfCommon`，两套渲染器共用。
2. 拆 `GenealogyService` 为 `SchemaMigrator` + `PersonRepository` + `BookRepository` + 门面。
3. 云同步收敛为 `CloudFacade`，内部按备份/拉取/发布/离队拆分。

### 阶段 4：模块化与资源化
1. 把 `common/base`、`common/ui` 建成 HAR，`entry` 只依赖 HAR。
2. 颜色/尺寸/文案迁移到 `resources`。
3. 人物列表与树卡片接入 `LazyForEach` + `@Reusable`。
4. 为 7 种树风格统一接口，新增风格只实现 Renderer。

## 七、收益与风险

| 项 | 预计收益 | 风险 |
|---|---|---|
| 死代码清理 | −300~400 行，减少误读 | 低 |
| 表单组件抽取 | PersonEdit 预计 −600 行，11 个页面统一输入体验 | 低 |
| 字段注册表 | 新增字段从 10 处改为 1 处，杜绝“保存不生效/云同步丢失” | 中：需逐字段回归 |
| PDF 公共层 | −300~500 行，内存策略统一 | 中：两套版式差异大，只合工具层 |
| 服务拆分 | 可测试性提升，单文件从 3,000 行降到 500 行级 | 中高：改动面大 |
| HAR 模块化 | 编译增量、职责清晰、可复用 | 高：构建配置与循环依赖 |

**不建议做的事：**

- 不建议合并 7 种树风格（版式差异是产品能力）。
- 不建议强行合并两套 PDF 渲染器（A4 牒记 vs 卡片分页）。
- 不建议把所有 service 改成继承基类（ArkTS 不鼓励，收益低）。
