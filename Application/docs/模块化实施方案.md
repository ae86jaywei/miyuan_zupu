# 模块化（HAR）实施方案

> 范围：`Application/`
> 目标：按 HarmonyOS 官方推荐把可复用代码拆成 HAR，`entry` 只保留页面与装配。
> 状态：方案文档，**未改动任何构建配置**。需要在 DevEco 环境验证后再执行。

---

## 一、为什么拆

当前所有代码在一个 `entry` 模块：

- `pages/` 14 个页面、`view/` 9 个、`components/` 18 个、`service/` 36 个全部混在一起。
- `components/*` 反向依赖 `service/*`（如 `SelectField` 依赖 `ScriptService`），无法独立复用。
- 编译是全量 HAP，改一行组件也要整包构建。

拆成 HAR 后：

- `common_base`：纯模型、工具、主题，可被任何模块依赖。
- `common_ui`：通用组件与表单控件，只依赖 `common_base`。
- `entry`：页面、业务服务、路由，依赖上面两个 HAR。

## 二、目标结构

```
Application/
├── common/
│   ├── DateUtil/              # 现有 HAR（保持不动）
│   ├── base/                  # 新 HAR：common_base
│   │   └── src/main/ets/
│   │       ├── model/         # Person / Enums / Genealogy / Stats / FieldRegistry
│   │       ├── util/          # TextUtil / StringUtil / IdGenerator / PatchUtil / RouterUtil
│   │       ├── theme/         # Theme
│   │       └── Index.ets      # 统一导出
│   └── ui/                    # 新 HAR：common_ui
│       └── src/main/ets/
│           ├── components/    # TS / PageHeader / BackButton / EmptyHint / InfoRow / StatCard / Tag
│           ├── form/          # SelectField / PersonPickerField / DateFieldInput / SearchField
│           └── Index.ets
└── entry/
    └── src/main/ets/
        ├── pages/             # 只保留 @Entry 页面（路由必须在 entry）
        ├── features/
        │   ├── person/        # PersonDetailPanel / DieRecord
        │   ├── tree/          # TreeCanvas + 7 种树风格 + TreeLayout / TreeCuller
        │   ├── export/        # PdfExportService / PagedPdf / RawPdfWriter / ExportService / ImportPlanner
        │   ├── family/        # HomeView / 成员 / 目录 / Catalog
        │   └── settings/      # SettingsView / StyleSwitcher
        ├── service/           # 数据库、云同步、账号、权限等业务服务
        └── view/              # 暂留，逐步并入 features
```

### 依赖方向（严格单向）

```
entry  ──►  common_ui  ──►  common_base  ──►  common/DateUtil
  └──────────────────────────►  common_base
```

禁止：`common_base` 依赖 `common_ui`/`entry`；`common_ui` 依赖 `entry`。

## 三、文件归属清单

### common_base（先拆，风险最低）

| 目录 | 文件 |
|---|---|
| `model/` | `Person.ets`、`Enums.ets`、`Genealogy.ets`、`Stats.ets`、`FieldRegistry.ets`、`PersonNode.ets`、`Scope.ets` |
| `util/` | `TextUtil.ets`、`StringUtil.ets`、`IdGenerator.ets`、`PatchUtil.ets`、`RouterUtil.ets`、`FlatListSource.ets` |
| `theme/` | `Theme.ets` |

**暂不迁**：`CloudModels.ets`（与云 payload 绑定，先留 entry）、`PrivacyService.ets`（业务）。

### common_ui

| 目录 | 文件 |
|---|---|
| `components/` | `TS.ets`、`PageHeader.ets`、`BackButton.ets`、`EmptyHint.ets`、`InfoRow.ets`、`StatCard.ets`、`Tag.ets`、`PersonAvatar.ets`、`SyncProgressOverlay.ets` |
| `form/` | `SelectField.ets`、`PersonPickerField.ets`、`DateFieldInput.ets`、`SearchField.ets` |

**前置条件**：`components` 当前依赖 `service/ScriptService`（`T`、`uiFontFamily`）。拆 HAR 前需要把 `T`/`uiFontFamily` 下沉到 `common_base/util`，否则 `common_ui` 会依赖 `entry`，形成反向依赖。

### entry（暂留）

| 目录 | 原因 |
|---|---|
| `pages/` | `@Entry` 页面必须在 entry 的 `main_pages.json` 注册 |
| `service/GenealogyService.ets` 等 | 依赖 `relationalStore`、业务数据，暂留 |
| `service/CloudSyncService.ets` 等 | 依赖 AGC/云函数，暂留 |
| `features/tree`、`features/export` | 依赖 PersonNode/TreeLayout/PDFKit，可后续独立 HAR |

## 四、构建配置改动（执行时）

### 4.1 `Application/build-profile.json5`

```json5
{
  "app": { /* 不变 */ },
  "modules": [
    { "name": "entry", "srcPath": "./entry", "targets": [{ "name": "default", "applyToProducts": ["default"] }] },
    { "name": "common_base", "srcPath": "./common/base" },
    { "name": "common_ui", "srcPath": "./common/ui" }
  ]
}
```

### 4.2 每个 HAR 的 `oh-package.json5`

```json5
{
  "name": "@miyuan/common_base",
  "version": "1.0.0",
  "description": "模型、工具、主题",
  "main": "Index.ets",
  "author": "",
  "license": "Apache-2.0",
  "dependencies": {}
}
```

`common_ui` 的依赖：

```json5
{
  "name": "@miyuan/common_ui",
  "version": "1.0.0",
  "main": "Index.ets",
  "dependencies": {
    "@miyuan/common_base": "file:../base"
  }
}
```

### 4.3 `entry/oh-package.json5`

```json5
{
  "dependencies": {
    "@miyuan/common_base": "file:../common/base",
    "@miyuan/common_ui": "file:../common/ui",
    "common_dateutil": "file:../common/DateUtil"
  }
}
```

### 4.4 每个 HAR 的 `hvigorfile.ts`

```ts
import { harTasks } from '@ohos/hvigor-ohos-plugin';
export default { system: harTasks };
```

## 五、迁移步骤

### 4A：common_base（纯 TS，风险低）

1. 新建 `common/base` 模块骨架（`oh-package.json5`、`hvigorfile.ts`、`Index.ets`）。
2. 搬 `model/`、`util/`、`theme/`。
3. `entry` 的 import 从 `../model/Person` 改为 `@miyuan/common_base`。
4. 先只改 import，不改逻辑；`hvigorw assembleHap` 验证。

**风险**：`common_dateutil` 目前被 `model`/`service` 使用，HAR 内也要声明依赖。

### 4B：把 `T`/`uiFontFamily` 下沉

1. 把 `ScriptService` 中的简繁转换与字体函数拆到 `common_base/util/Script.ets`、`UiFont.ets`。
2. `ScriptService` 保留业务字典加载，内部调用下沉后的函数。
3. `components` 改依赖 `common_base`，为 `common_ui` 拆出扫清障碍。

### 4C：common_ui

1. 新建 `common/ui` 模块骨架。
2. 搬 `components/*` 与 `components/form/*`。
3. `entry` 改 import 为 `@miyuan/common_ui`。
4. 验证所有页面编译与交互。

**注意**：`PersonPickerField` 依赖 `GenealogyService`（业务）。拆 UI HAR 前需要把它改为**数据注入**：

```ts
onSearch: (keyword: string) => Person[] = () => [];
onResolve: (uid: string) => Person | null = () => null;
```

由页面传入 `GenealogyService` 的查询函数，避免 UI 反向依赖业务。

### 4D：feature HAR（可选）

把 `tree`、`export` 拆成 `@miyuan/feature_tree`、`@miyuan/feature_export`，体积大、收益中等，建议最后做。

## 六、迁移前必须先解决的耦合

| 耦合 | 位置 | 处理 |
|---|---|---|
| UI 依赖 `ScriptService` | `components/*`、`form/*` | `T`/`uiFontFamily` 下沉 common_base |
| UI 依赖 `GenealogyService` | `PersonPickerField` | 改为回调注入 |
| `Theme` 被 service 引用 | `PdfTheme`/打印相关 | 允许 service 依赖 common_base |
| `PersonNode` 依赖 `TreeLayout` | `model/PersonNode` | 一起放 common_base 或 feature_tree |
| `CloudModels` 依赖 `Person` | 云端映射 | 留 entry，或随 `Person` 一起放 common_base |

## 七、验证清单（执行时必做）

1. `hvigorw clean assembleHap --mode module -p product=default` 编译通过。
2. `hvigorw --sync` 无依赖环告警。
3. 真机/模拟器回归：
   - 首页、成员、目录、树、详情、编辑、导入导出、设置、登录、分享、协议、日历、地图、审核。
4. 资源检查：HAR 内 `resources` 是否被正确合并，`$r('app.media.xxx')` 是否可解析。
5. 签名与打包：HAP 签名配置不变。

---

## 八、不建议现在做的事

- **不要在没有 DevEco 的环境中直接改 `build-profile.json5`**：模块路径、`hvigorfile.ts`、HAR 清单任一错误都会导致整个工程无法构建。
- 不要一次性搬全部文件：先 `common_base`，再 `common_ui`，每次构建验证。
- 不要把 `pages/` 搬出 entry：路由注册在 entry，搬出会导致页面无法启动。
- 不要为了拆分而拆分 `service/*`：数据库、云同步、PDF 与业务强绑定，先留在 entry。

## 九、收益预估

| 项 | 收益 |
|---|---|
| `common_base` | 模型/工具/主题可被独立复用；编译增量更小 |
| `common_ui` | 表单与顶栏可复用到其他鸿蒙项目 |
| `entry` 精简 | 页面与业务分离，职责更清晰 |
| 构建 | HAR 变更只重编 HAR，HAP 链接更快 |

## 十、结论

阶段 4 的技术方案已经明确，但**必须在 DevEco + HarmonyOS SDK 环境中执行和验证**。当前环境的连续重构已经完成阶段 1–3，建议先做真机回归，再启动 HAR 拆分。
